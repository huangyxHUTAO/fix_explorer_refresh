# fix_explorer_refresh

让 Windows 资源管理器在文件夹内容变化后**重新排序**。

新建一个文件，它不会蹲在列表末尾不下来；改名、改内容、新建，会自动重新排序。

不注入、不改系统文件、不用管理员权限，只用公开 API。跑起来生效，退出即恢复原状。

---

## 快速开始

1. 下载 `fix_explorer_refresh.exe`，或按「构建」一节自己编译
2. 双击运行。会开一个控制台窗口，一直待着
3. 正常用资源管理器 —— 打开的文件夹会自动被跟踪
4. 不想要了：关掉那个窗口，或双击 `stop.bat`

不需要任何配置。想让它写日志就加 `--log`。

**不想看到控制台？** 双击 `start_background.bat` —— 它在后台启动、不留窗口，日志自动写到 exe 同目录的 `<exe名>.log`。要停就双击 `stop.bat`。

## 现象

```
1. 资源管理器按名称升序排列某个文件夹
2. 在该文件夹里新建一个文件（命令行、别的程序、拖拽都算）
3. 新文件出现在最底部
4. 等 1 秒、10 秒、1 分钟 —— 它还在最底部
5. 按 F5 —— 立刻跳到正确位置
```

同一个文件夹，有时候新建文件会**直接出现在正确位置**，有时候会**先出现在底部、几百毫秒后跳上去**，有时候**永远留在底部**。同一台机器、同一个文件夹，连续跑三次，结果可能三种都不一样。

按"修改日期"排序时同样有此问题：改一个文件的内容（mtime 变了），那一行不会移动。

---

## 为什么会这样

以下结论来自对 `shell32.dll` / `windows.storage.dll` 的静态分析和运行时跟踪。文中只描述"什么条件下发生什么"，任何人在自己机器上都能复现。

### 1. 增量插入不做排序

新增单个文件时走的插入路径，索引参数是常量 `INT_MAX`：

```
索引参数被硬编码成 INT_MAX，通用插入函数内部把它夹到 count，
效果等价于"无条件追加到末尾"。
```

这条路径里没有任何比较、二分或排序调用。

### 2. 排序只由"整目录重新枚举"产生

真正会排序的是枚举任务 `CEnumTask`（用 `IShellFolder2` 的比较函数排完整批），排好后整批推给视图，视图清缓存并重建（`CListViewHost::OnCollectionChanged`）。

### 3. 那次重新枚举靠一条不保证送达的通知

触发重新枚举的是目录级变更通知 `SHCNE_UPDATEDIR`：

```
SHCNE_UPDATEDIR
  → 集合对象识别到这是"目录级变更"
    → 决定重新枚举
      → 新建枚举任务，整目录重扫、排序
        → 批次推给视图 → 视图重建
```

而这条通知发不发，由文件系统通知层按一组内部 flag 决定。**同一个操作，有的目录会收到"创建 + 更新属性 + 目录变更"三条，有的只收到前两条。**

只收到前两条时：文件被正常加进列表（加在末尾），但没有任何"请重排"的指令到达，于是它永久留在末尾。

### 4. 实测证据

同一个最小宿主程序、同一个目录，连续三次：

```
run1  文件创建后 4 秒全程 idx=末尾
run2  t=0ms 就已经在正确位置
run3  文件创建后 4 秒全程 idx=末尾
```

所以**这不是目录属性问题**——换文件夹类型、删视图缓存、改注册表、重启 explorer 都无效，因为变量不在这。

### 5. 小结

两个模块的假设没有接上：**集合层假设"新增会被后续的枚举批次纠正"，而通知层只在特定条件下才发出那条能触发纠正的通知。** 落到中间的这类变化，就只能永久停在末尾。

## 这个工具做什么

监视你当前打开（或被指定）的文件夹，一旦内容有变化，就补发一条 `SHCNE_UPDATEDIR`：

```c
SHChangeNotify(SHCNE_UPDATEDIR, SHCNF_IDLIST | SHCNF_FLUSH, pidl, NULL);
```

也就是**把系统自己定义、本该发、但不保证发的那条通知补上**，让资源管理器走它自己的重排路径。

- **变化判定**：文件名 / 大小 / 最后写入时间，任一项变化都算 —— 所以新建、改名、改内容全部覆盖
- **消抖**：静默 400ms 后才发。连发一批文件（解压、批量拷贝）只触发一次重排，不是每个文件都跳一下
- **自动发现**：每 2 秒枚举当前所有打开的文件夹，**包括 Win11 的标签页**（标签页各自算一个视图）；窗口关掉自动停止监视
- **默认不落盘**：打开的文件夹路径只打在你自己的控制台里；加 `--log` 才写文件

## 用法

```
fix_explorer_refresh.exe                     自动跟踪所有打开的文件夹，只打控制台
fix_explorer_refresh.exe --log               同上，并把日志写到 exe 同目录的 <exe名>.log
fix_explorer_refresh.exe "D:\x" "D:\y"       额外监视指定目录（没开窗口也能盯）
fix_explorer_refresh.exe --log "D:\x"        组合
fix_explorer_refresh.exe --no-auto           关闭自动发现，只监视显式指定的目录
fix_explorer_refresh.exe --now "D:\x"        只补一次通知，立刻生效，不常驻
fix_explorer_refresh.exe --detach            后台启动：不显示任何窗口，自动带 --log
fix_explorer_refresh.exe --stop              停止正在运行的后台实例
fix_explorer_refresh.exe --version           显示版本和编译时间
taskkill /f /im fix_explorer_refresh.exe     强制停止（不推荐，优先用 --stop）
```

**单实例**：同一时间只允许跑一个。第二个启动会直接提示并退出，避免同一条变更被补两次通知、触发两遍重排。`--detach` 也会检测——已有实例时返回 `not started: another instance is already running`。

**`--detach` 说明**：以无窗口方式重新拉起自己（`CREATE_NO_WINDOW`），父进程确认子进程活下来之后才退出，所以 Ctrl+C 或关闭终端不会带走它。因为无窗口就没有控制台输出，它会自动补上 `--log`。

**可选名单**：exe 同目录放一个 `watchlist.txt`，一行一个目录，运行时每 2 秒重读。加行即开始监视，删行即停止。

### 日志格式

```
[05:51:55.599] [diff] + zz-new.txt      (E:\test\subtest)
[05:51:56.131] [notify] 补发重排 diff=1 攒了422ms   (E:\test\subtest)
[05:51:56.658] [diff] - zz-new.txt      (E:\test\subtest)
[05:51:56.658] [diff] + zz-renamed.txt  (E:\test\subtest)
[05:51:57.180] [notify] 补发重排 diff=2 攒了437ms   (E:\test\subtest)
[05:51:57.607] [diff] ~ 001             (E:\test\subtest)
```

| 标记 | 含义 |
|---|---|
| `[watch] ...` | 开始监视。后面标 `(自动发现)` 或 `(名单)` 表示来源；都没标是从命令行来的 |
| `[watch] 停止监视 ...` | 窗口关掉了 / 从名单里删了，不再跟踪 |
| `[snap] N 项` | 首次扫描的基线。**只在启动后出现一次**，不触发重排 |
| `[diff] + / - / ~` | 新增 / 删除 / 修改（大小或 mtime 变了） |
| `[diff] ... 另有 N 项未逐条列出` | 一批变化太多，逐条日志最多打 20 条 |
| `[notify] diff=N 攒了Xms` | 真正补发通知的时刻，以及攒了多久才触发 |
| `[auto ] 跳过虚拟位置：...` | 此电脑、网络这类非文件系统位置，跳过 |
| `[err  ] 无法枚举 ...` | 权限不足 / 网络盘断开等。**错误码变化时才打**，不会刷屏；恢复时打 `[err ] 恢复枚举` |
| `[skip ] 路径过长` | 长度 ≥ 259 字符的路径，本版本不支持 |

## 如何自行验证

不需要任何逆向工具，两步就能确认。

### A. 确认现象存在

1. 资源管理器按名称升序排列一个文件夹
2. 在里面新建一个文件（命令行 `echo x > 文件名` 最直观，避免鼠标操作引入干扰）
3. 观察：它出现在最底部，并且长时间不动；按 F5 立刻归位

同一个文件夹重复几次，你会看到它**有时直接出现在正确位置** —— 这正是"收到的通知集合不同"的结果。

### B. 确认"补一条目录变更通知就能修好"

1. 让现象重现（文件停在底部）
2. 执行 `fix_explorer_refresh.exe --now "那个文件夹"`
3. 列表应在几百毫秒内归位

这一步是整篇分析的核心：**排序逻辑本身没坏，缺的只是那条通知。**

## 限制

- **运行时生效**：进程退出后现象恢复原状。长期用可以 `--detach` 挂后台，或者把 `start_background.bat` 的快捷方式放进 `shell:startup`（开机自启）。
- **每次触发是一次整目录重新枚举**：滚动位置可能被拉回顶部，多选可能丢失；几万文件的目录会有明显开销（这一点和你在资源管理器里按 F5 的代价相同）。这类目录可以用 `--no-auto` 只挑你关心的文件夹。
- **只监视目录本身一层**，不递归子目录。子目录里的变化要在那个目录也开着窗口（或写进名单）时才会被注意到。
- 路径长度上限 259 字符（含），更长的路径会被跳过并在日志里标记。
- **已验证环境：Windows 11 24H2（build 26100）x64 单机**。只用了公开 API，理论上 Windows 10 / 其他 Win11 版本同样适用，但**未实测**。遇到问题请附上日志和系统版本。

## 常见问题

**这是修 bug 吗？**
它让排序视图恢复"列表恒有序"这个不变式，但**没有改变系统任何一方的行为**——增量插入仍然不排序，通知层仍然可能不发那条通知。进程一停，现象就回来。

**为什么不直接注入 explorer 改那行排序逻辑？**
因为不需要。补一条系统自己定义的通知就能达到同样效果，而且不碰 explorer 内存、不需要管理员、不绑程序版本号，微软将来改了什么它也只是退化成空操作。

**它会拖慢我的电脑吗？**
每个被监视目录每 100ms 做一次目录枚举（`FindFirstFile`）。几个普通文件夹的开销可以忽略；如果你开着上万文件的目录，建议把它从名单里去掉，或者不开这个工具。

**杀软报毒 / SmartScreen 拦截？**
可能。它的行为特征（枚举窗口、监视目录、调用 `SHChangeNotify`）和某些恶意软件同类。源码在此，可自行编译；预编译版未签名。

**为什么 `--stop` 用 TerminateProcess 而不是优雅退出？**
因为这个工具没有任何需要落盘的状态——被杀和正常退出没有区别。日志是逐行 flush 的，不会丢。

**能不能只对某个目录生效？**
可以，加 `--no-auto` 关闭自动发现，只监视你在命令行或 `watchlist.txt` 里显式列出的目录：

```
fix_explorer_refresh.exe --no-auto --log "D:\x" "D:\y"
```

## 构建

MinGW-w64 x64：

```
gcc -O2 -municode -s -o fix_explorer_refresh.exe fix_explorer_refresh.c -lole32 -loleaut32 -luuid -lshell32 -lshlwapi -luser32
```

或者直接跑 `build.bat`（MinGW）/ `build-msvc.bat`（Visual Studio 命令行）。

`-municode` 在 GCC 下是必须的（源码用了 `wmain`）；MSVC 不需要。

单文件、无第三方依赖、无资源文件。
